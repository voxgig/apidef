# Implementation rationale

Entity action request bodies describe arguments, and their response bodies describe results. Neither automatically describes the entity record. Field inference must distinguish these from an entity's own component schema; otherwise generated entity types acquire action-only fields.

The TypeScript and Go implementations share ordering and classification semantics. Stable iteration and case-preserving name normalization are part of parity, not cosmetic formatting. The agent guide and architecture decisions describe the canonical implementation and correction surface.

Sources: [field inference](ts/src/transform/field.ts), [Go field inference](go/transform_field.go), [normalization](ts/src/utility.ts).

Reference resolution in the TypeScript parser replaces each `$ref` site with a copy of its target and then walks the copy. A site met again inside its own copy, as when a schema is its own direct item, receives that copy rather than a new one: the cycle closes, and the decycle pass cuts it. Without the guard the walk copies the target forever whenever the paths precede the components. The Go parser resolves a site in place, so the site itself is already visited and needs no guard.

Sources: [parse](ts/src/parse.ts), [Go parse](go/parse.go).

A JSON pointer resolves to an object or to nothing. A segment names an own key, or an RFC 6901 array index, and an alias met anywhere on the way is followed, its own keywords laid over its target. Following aliases at every step, not only at the end, is what makes the answer independent of the order in which the walk replaces sites: the TypeScript walks in document order and the Go in sorted key order, so a pointer passing through an alias found the target in one port and nothing in the other, depending on which had replaced the alias first. Order also reaches a chain that ends at a missing target: an unresolved alias gains an `x-ref`, which a later chain would read as a sibling keyword, so a chain that ends at no object is unresolved whatever its siblings. A string, list or null target is unresolved rather than spread into an object whose keys are character or element positions. Path keys lose the quotes an explicit YAML key keeps before resolution, since a pointer never spells those quotes; colon parameters become braces after it, so a pointer names a path as written and a parameter declared through a reference counts. A rename onto a key another path has, or would also get, is not made, because the last one in the document winning needs a document order Go does not keep.

Text is compared and written as the TypeScript sees it. A lone surrogate cannot survive the Go parser, so the TypeScript replaces it with U+FFFD after the parse, merging keys that become equal as the parser merges a repeated key. The Go port decodes ill-formed UTF-8 as Node does and sorts by UTF-16 code unit where the TypeScript uses the default sort. Both parsers join an escaped surrogate pair into the character it spells, in JSON and in a YAML double-quoted scalar alike.

Sources: [parse](ts/src/parse.ts), [Go parse](go/parse.go), [Go sorting](go/utility.go).

The guide's schema rates count component references per use in the resolved spec, not per object: a reference reached through a shared response counts once for every route to it, which is the measure the rate thresholds were calibrated on. A `$ref` chain resolves to its first label, because the TypeScript parser collapses the chain into one copy under that label, so an intermediate link counts only where it is written, not once per use of the alias. The count is a path count over a graph whose nodes are reference labels together with the keys an occurrence overrides, so shared structure is scanned once per node rather than once per use. A node key joins its parts with NUL after escaping NUL and U+0001 inside each part, so no label can spell another node's key or the root's; a part holding neither character is unchanged, and so is the order the cut depends on. A reference cycle is cut at the back-edges of a depth-first search that visits successors in code point order, the order Go's byte sort gives, so both ports cut the same edge. The TypeScript parser replaces each cycle's closing edge with a marker string and records the edge in a table the count reads, so the count sees the graph as resolved; the Go parser leaves cycles in place. Counts saturate at one billion, far above any threshold, so a spec whose uses multiply stays finite.

Sources: [count](ts/src/refcount.ts), [Go count](go/refcount.go), [guide](ts/src/guide/heuristic01.ts).

A response envelope does not name an entity: the record it carries is judged in its place, found through the same `envelopeProp` test the field transform unwraps with, so a name and the fields beneath it come from one schema. The naming test is narrower than `envelopeProp`, which accepts any record whose only structured property is one list or one nested object; naming such a record after what it holds renamed and merged real entities, so an envelope must declare no `id`, a single-item envelope must hold nothing but the item, and a page nothing beside its records but the paging fields `ENVELOPE_PAGING_PROPS` lists. A balance beside a list of errors, a report's totals beside its suites, or a scope setting beside the repositories it covers is a record. Whether a schema is an envelope is decided once, over every operation that answers with it (`MeasureEnvelope`): a member list that the list operation unwraps and the create returns whole would otherwise split one resource between two names. An operation unwraps only the response `ResolveTransform` reads, its 200, else its 201, else its 202, so a schema it answers with in another success response never names through it, and naming stays a subset of unwrapping. A 202 is read but names nothing, because its body may describe the accepted work rather than the resource, except for a read whose 202 record another operation answers with in a 200 or 201 (`namingSchemas`): the other answer shows the record is a resource, and SaladCloud's instance read otherwise split one resource between its tag and its record. Both answers are compared through their envelopes (`namingRef`), as everything else that names reads them, so a record a 200 carries only inside an envelope still qualifies. A write keeps the rule, because a verb answering the record it acts on, such as GitHub's fork or transfer, is still a verb on that record. A record that more than one envelope carries is named through none of them (`MeasureEnvelopeItems`): the envelopes' own names are what tell the resources apart, and naming both after the record merged package and entitlement usage metrics into one entity whose loads took the same parameters. One page and one single-item envelope still name through the record when a route of the item lies at or beneath a route of the page (`isPageAndItsItem`), as Mux's job list and job cancel do; counting them against each other split one resource between its path names, and dropping the route test merged unrelated resources that share a record. A page may carry one metadata object beside its records (`PAGE_META_PROPS`: Vapi's `metadata`, Neon's `pagination`, Maxio's `meta`), which is not a second candidate; the exclusion needs the remaining list to hold records, because GitHub's feed holds a list of URL strings beside its `_links`, and a composed item holds records only when one of its branches is an object. A page with no scalar of its own beyond status and paging reads its one list of records past a list of scalars or an object beside it (Mux's `timeframe`, Novu's `filter`), since a list operation returns a list and nothing else there can be one; a scalar of its own, such as a combined status's `state`, makes it a record that holds a list. A composed page reads the same way (Neon's branches beside their annotations), though a composed record keeps the strict rules. The naming test does not follow: `strictEnvelopeProp` still wants nothing beside a page's records but paging, so unwrapping widens and naming does not. A property named after the entity unwraps a response only when the response is not the entity's own component (SaladCloud's container group, GitHub's commit), compared by the name left after the wrapper suffix is cleaned, so a `UserResponse` that names `user` still unwraps, and wraps a request only when it is structured and is the whole body (SaladCloud's create, GitHub's new SSH key); both rules used to fire on any property with the entity's name. The operation an envelope is judged for is resolved before the entity is named, from the same path shape `ResolveEntityName` then matches.

Sources: [envelope](ts/src/utility.ts), [guide](ts/src/guide/heuristic01.ts), [Go guide](go/guide.go).

A response property is a candidate envelope item, or a wrapper under the entity's name, only when it could hold a record. A scalar is data however it is composed: an `allOf` that `collapseScalarAllOf` reads as one scalar, the rule the field transform types a field with, and a `oneOf` or `anyOf` whose branches are scalars or `null`, since a null branch only makes the value nullable. Counted as structured, such a property makes a record that holds an id beside a status read as an envelope around the id, and its load answers with the id. Sharing the field transform's rule keeps the two readings in step: a property a field types as a string is never what a response unwraps to. Any other composition stays structured, such as an `allOf` around an object or a union with an object branch.

Sources: [wrapper](ts/src/utility.ts), [Go wrapper](go/utility.go), [field](ts/src/transform/field.ts).

A trailing path parameter under its entity's segment is renamed to `id` from the path alone; the response component has no veto. The component an item operation answers with is routinely named for one view of the entity (`CargoUpstream`, `PushOperation`, `branch-with-protection`), so a guard requiring that name to match the entity withheld `id` from real keys far more often than it caught a parameter naming a scope, such as a namespace `{owner}`, and that case is corrected in the guide.

Sources: [guide](ts/src/guide/heuristic01.ts), [Go guide](go/guide.go).

A parameter's name is decided for its entity, not for one path. The path rules read a parameter's place, and one parameter sits at different places in an entity's list, item and action paths, so a parent key kept the specification's name in a list and became `<parent>_id` in the item (SaladCloud's `project_name` beside `project_id`). After collection merging, which moves paths between entities, a parameter at the same place in several of an entity's paths, with the same segments before it, takes its own name in snake case wherever the paths disagree (`entityParamNames`). The entity's own key is excluded: a list keyed by its parent passes the trailing-key rule (Cloudsmith's `/repos/{owner}/`), and spreading that `id` would make an owner the identifier of every repository route. A parameter whose name says it holds a name is never derived as `<parent>_id` (`isNameParam`).

Sources: [guide](ts/src/guide/heuristic01.ts), [Go guide](go/guide.go), [fixture](ts/test/entity-param-names.tsv).

A rare response schema that two or more path resources answer with is a shape they share, and each route keeps its own path's name (`sharedRoutes`). Path names alone overcount resources: filters, selectors, actions that return their target, relations and legacy route spellings give one resource's records a second name, and naming them after their paths split resources and merged unrelated ones. So a schema that declares an `id` is a record and never shared; a route beneath a path naming another resource of the same schema is a view and does not count; item routes with the same parent and the same parameters are aliases and count once, while collection routes with the same parameters are sibling collections and count apart; and a name is withheld from every route when taking it would merge two schemas or two routes with one operation and one parameter set, because withholding it from one route only would leave the family split between two names. The decision is made once, over every route, before any method is named, since a route's resource and its schema's identity do not depend on naming order. A schema declares an `id` at any depth of `allOf` (`declaresId`), since an identifier is commonly inherited through a chain of base schemas.

Sources: [guide](ts/src/guide/heuristic01.ts), [Go guide](go/guide.go), [fixture](ts/test/shared-routes.tsv).

The guide can override inferred composite identity with explicit `id.parts`, or disable inference with `id.composite: false`. An empty parts list is not a reliable opt-out because model resolution can omit it. Edit canonical schemas under `model/` and synchronize the packaging mirrors.

An entity whose every operation is an access-token exchange is emitted with the default `active: *false` and a comment naming the reason, never dropped, so `guide.aontu` can switch it back on. The tally counts only the operations a method resolves to: a method with no CRUD mapping becomes no operation, so it can neither deactivate an entity nor keep one active. Method selection carries each operation's own `security` for this test alone.

Sources: [detection](ts/src/utility.ts), [Go detection](go/utility.go), [guide](ts/src/guide/heuristic01.ts), [Go guide](go/guide.go).

An entity that collection merging leaves with no path is removed, in both ports, rather than emitted with `active: *false`: the owner's explicit call under ADR-002, since an entity with no path is not a classification `guide.aontu` could switch back on. Sources: [merge](ts/src/transform/entity.ts), [Go merge](go/transform_entity.go).

A collection joins a route beneath its literals by the shape of the route first and the record second. An item route owns it whatever record it answers with, because a list's records are routinely a summary of the item's (Apicurio's searched groups beside a group's metadata, GitLab's runners beside a runner's details), and the record only breaks a tie between item routes on different entities, which a tag naming the delete and the record naming the read produce. A deeper route owns it only on the record, since its shape cannot say whether it is a verb on the collection's own record, such as Cloudsmith's token refresh or Mux's job cancel, or a sub-collection of another, such as GitHub's plan accounts or Mux's metric breakdowns. Comparing record names cannot veto an item route: vendors name a create's answer apart from the record it creates (Vapi's CreateSimulationRunResponse beside SimulationRun), so a name mismatch there says nothing. Comparing the records can: a share whose own record declares an `id` and shares no more than half of its properties with the item's stays apart (`distinctRecord`), as GitLab's runner registration does, while a record without an `id`, such as a ticket a create answers with, joins as before. Both records are read from a 200 or 201 only (`distinctShare`): a create whose only answer is a 202 job record would otherwise stay apart on the job's entity, against the rule that an Accepted body names nothing. An item route that answers nothing, named from a tag that names another resource with a record, takes the entity its collection's record names when that record carries the collection path's name (`itemOfCollection`), since joining the collection to the tag's entity carried GitHub's invitation fields onto repositories; a tag that names no resource, such as a `Settings` group, keeps the join. Ties sort by code point, so the ports need no shared insertion order. The records come from `routeRecordRef`, which reads the guide's success response through the same envelope rules the transform unwraps with.

Collection merging runs in the guide stage only; the entity transform takes the unified guide as given, since merging again would move a path `guide.aontu` assigns and delete the entity it re-declares. Sources: [guide](ts/src/guide/heuristic01.ts), [Go guide](go/guide.go).

A success response is recorded whenever it declares a body, JSON alone included, because a client asking for JSON must be told apart from one that should ask for nothing; a response's `encoding` is ignored, as OpenAPI applies it to request bodies only, and Swagger's `type: file` is bytes on either side. A point records its request body only when the body is not JSON alone, so a model whose bodies are all JSON is unchanged and a generator that does not read `rb` sends what it always sent. A range that admits JSON (`*/*`, `application/*`) is JSON unless its schema says bytes outright, because reading it as raw would turn a working JSON request into bytes; under a named media type that is not JSON, a schema that constrains nothing is bytes, as OpenAPI 3.1 defines it. A raw body is binary unless its schema says text (`format: byte`, `contentEncoding`) or its media type is text and its schema typed, since bytes can carry text and text cannot carry bytes. Media types are ranked by kind and then by code point, never by declaration order, which the Go parser does not keep. The choice is a default that `body.media` in `guide.aontu` replaces; the base guide does not write it, so the guide goldens are unchanged and a concrete value there has nothing to clash with. A point reads the entry of its own operation, since two operations can share a path and method; the entry's method must match the point's, and a `PATCH` promoted to `update` reads its `patch` entry. `text/json`, which .NET definitions list beside `application/json`, is JSON, so their bodies record nothing. A Swagger array is one delimited value unless its `collectionFormat` is `multi`, and a field records which (`join` or `list`), because `csv` is the default. A media type the guide names is matched against the declared keys before ranges are normalised, so a chosen `multipart/*` keeps its schema. Swagger 2 `body` and `formData` parameters stay among the query arguments, where the argument transform puts every parameter of an unknown location: the body model describes a form's fields as well, and removing the parameters would change selectors, those of every Swagger 2 JSON operation among them.

Sources: [request body](ts/src/transform/body.ts), [Go request body](go/transform_body.go), [fixture](ts/test/request-body.tsv), [guide fixture](ts/test/body-guide.tsv).

A point lists the properties its JSON request body declares (`bf`) from the schema `requestFieldSchema` returns, the one the field transform reads request fields from, so the two cannot disagree about which media type or which wrapper property holds the record. The list is the body's own declaration rather than the entity's: an action's arguments and a QUERY filter are listed although neither becomes a field, because a generator asks which names the body holds, not which fields the entity has. For the same reason it reads `oneOf` and `anyOf` members as well as `allOf` ones, which the field transform does not: GitHub's codespace create and its issue labels take one of several objects, and reading `allOf` alone would say they declare nothing. An array body lists the field the request data sends it from, since that is the name the body is built from. A body that declares nothing writes `false`, never an empty list: aontu resolves an optional key holding an empty list to no key at all, and the clean transform drops empty lists, so an empty list would arrive as the missing key that a model written before the key also has. A body that is not JSON lists nothing, as `rb` says how it is sent, and nor does an operation that declares no body, unless the guide names a JSON body media for it, which reads as a body that declares nothing (`false`).

Sources: [body fields](ts/src/transform/body.ts), [Go body fields](go/transform_body.go), [fixture](ts/test/body-fields.tsv).

A placeholder that shares its path element with other text, such as `{threadId}` in `{threadId}.json`, stays inside the element's literal segment (ADR-003), spelled with the name the argument transform gives its parameter (`nameLitParams`, `paramName`): the runtimes substitute each path argument by that name anywhere in the joined path, so the definition's own spelling went out unfilled wherever a rename or the snake-case form changed it. A segment of pieces would let a runtime walk the path without a pattern, but every runtime would have to learn it first; the spelling needs no consumer change. The same element names no verb (`isVerb`), so `{threadId}.json` no longer becomes an action named after its placeholder. A parameter with no `in` is matched to a placeholder by its exact name, the rule OpenAPI gives a path parameter: matching a canonical spelling, such as `thread_id` against `{threadId}`, would name the argument after the parameter while the path segment takes the placeholder's rename, and the request would go out unfilled. Only an absent `in` consults the path; an unknown one, such as Swagger 2's `body`, stays a query argument. A parameter placed on the path that way is required, as every path parameter is, and is named by `paramName`, as a placeholder with no parameter is, so a rename keyed by the definition's own spelling, such as `file.name`, names the argument as it names the segment. A custom method (`/schedules:count`) reads as its verb written as a trailing segment (`verbParts`) where an action is named and where a parameter is renamed by its place, but not where an entity is named: read that way, untagged counts on different resources would join one `count` entity.

Sources: [segments](ts/src/transform/entity.ts), [Go segments](go/transform_entity.go), [arguments](ts/src/transform/args.ts), [Go arguments](go/transform_args.go), [guide](ts/src/guide/heuristic01.ts), [Go guide](go/guide.go), [fixture](ts/test/path-segments.tsv).

Postman writes a server variable as `{{name}}`, and OpenAPI reads only the inner pair as the variable, so the outer braces would stay in the base URL a generated SDK builds. The top transform rewrites a run of exactly two braces around a name of letters, digits and underscores, the names the generated SDKs substitute, and declares each rewritten name the server does not with an empty default, so the SDK asks its caller for it. Any other run of braces is kept as the definition wrote it: `{{base-url}}` as `{base-url}` would declare a variable no SDK substitutes, and `{{{name}}}` has no single reading. The Go port normalises copies of the servers, since its list still holds the definition's own maps, and gives a URL with no scheme `https://` there as the TypeScript does.

A server variable that opens a URL stands for its origin when nothing but a path, query or fragment follows it, and for its scheme when `://` does, so the scheme default is not added there: by Postman's convention `{{baseUrl}}` holds `https://api.example.com`, and a prefix would double the scheme. A variable followed by anything else is part of the host, as in `{region}.example.com`, and keeps the default. A rewritten origin variable is described as the origin with its scheme, so the SDK tells its caller to pass the scheme in the value; a declared one is left as the definition declares it.

Sources: [top](ts/src/transform/top.ts), [Go top](go/transform_top.go), [fixture](ts/test/servers.tsv).
