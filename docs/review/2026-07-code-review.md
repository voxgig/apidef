# apidef code review — TypeScript, Go, and parity

**Date:** 2026-07-25 · **Scope:** `ts/src`, `go/`, the shared `*.tsv` fixture
mechanism, `go/validate_test.go`, CI, and the external `apidef-validate`
golden corpus.

Reviewed independently for TypeScript and Go, then reconciled. Every finding
below was reproduced by running code — commands and observed output are given
so each can be re-checked. Findings that rest only on reading (not execution)
are labelled **[code-read]**.

Baseline: both suites are green as reviewed — TS 438 tests pass, `go test
./...` passes. Nothing here is a failing test; it is all behaviour the tests
do not reach.

---

## 1. Verdict

The pipeline design is sound and the code is unusually well commented — most
non-obvious decisions carry a rationale comment, which made this review much
faster than it would otherwise have been.

The central problem is not in either implementation individually. It is that
**the parity mechanism cannot detect the divergences that actually exist.**
No test anywhere runs both implementations on the same input and compares the
results. The Go suite compares Go against frozen artifacts generated by an
older TypeScript build, and those artifacts are now stale. As a result the two
implementations have drifted apart substantially — on real specs they disagree
about entity sets, field names, field types, and operation assignment — while
every check stays green.

Two additional defects are serious in their own right, both in the canonical
TypeScript side, and both of which the Go port gets right:

- a valid OpenAPI spec whose schema is named `Constructor` crashes the build;
- chained `$ref` aliases silently lose their schema, order-dependently.

Priorities, in order: (1) build a real cross-language differential test,
(2) fix the two TS correctness bugs, (3) close the naming-primitive
divergence, (4) run Go in CI at all.

## 3. The parity mechanism (highest priority)

### 3.1 No test compares the two implementations — the check is Go vs. frozen artifacts

`go/validate_test.go` is the only "parity" test. It never executes the
TypeScript. It compares Go against files checked in earlier. Those files have
gone stale, and the repo's own fixture now demonstrates it:

| source | entities for `foo-1.0.0-openapi-3.1.0` |
|---|---|
| checked-in golden `apidef-validate/v1/guide/foo-…-base-guide.aontu` | `bar bax foo qaz taf yike zed` |
| current **Go** | `bar bax foo qaz taf yike zed` — matches |
| current **TypeScript** (canonical) | `bar bax foo `**`qiz`**` taf `**`xtra`**` zed` — does **not** match |

`TestValidateGuide/guide-foo-1.0.0-openapi-3.1.0` **passes**. The canonical
implementation has moved, the port has not, and the harness is structurally
incapable of noticing because TypeScript is never run.

Corroborating: running current apidef over the corpus rewrites **14** of the
checked-in `*-base-guide.aontu` files (observed via `git status` in
`apidef-validate` after a full-pipeline batch). The goldens are stale across
the board, not just for `foo`.

> Note on a hypothesis I tested and rejected: this is *not* a
> non-idempotency bug. Three consecutive full builds from a pristine guide
> produce identical output (cloudsmith 140/140/140) and leave the guide file
> byte-identical. The rewrites are a one-time catch-up of stale goldens.

### 3.2 `ts/test/model-ref/*.json` are generated by Go, not by TypeScript

```go
// go/validate_test.go:177
refDir := filepath.Join("..", "ts", "test", "model-ref")
…
// go/validate_test.go:~245
if _, err := os.Stat(refFile); os.IsNotExist(err) {
    os.WriteFile(refFile, goJSON, 0644)   // "First run: create reference"
```

Nothing under `ts/` reads or writes that directory — verified by grep; the
only references anywhere in the repo are the two lines above. So
`TestValidateModelData` is a **Go-vs-Go** regression test. It is valuable as
that, but it is not a parity check, and living under `ts/test/` actively
implies otherwise.

### 3.3 The comparisons that do run are written to tolerate divergence

In `go/validate_test.go`:

| site | behaviour | what it hides |
|---|---|---|
| `EXTRA Go entity` | `t.Logf` (only *missing* is `t.Errorf`) | Go may invent any number of entities |
| `FIELD COUNT DIFF` | `t.Logf`, commented "Go may extract more fields than TS which is acceptable" | an explicit, permanent parity waiver |
| `stripKeys(ent, "active")` | strips a Go-only field before comparing | a real structural difference |
| `normalizeForCompare` | collapses `` `$ARRAY` ``/`` `$OBJECT` `` → `` `$COMPOSITE` ``, commented as handling "non-deterministic field type values from map iteration order" | a *known* nondeterminism normalised away instead of fixed |

Also vacuous passes: petstore's `store` entity logs `0 fields match` — zero
fields on both sides compares equal and reports success.

### 3.4 Roughly 150 lines of `validate_test.go` are dead

Verified by grepping call sites (each appears only at its own definition):

- `deepEqualNormalized` (L311) — never called
- `structuralEqual` (L370) — never called
- `countFields` (L445) — never called
- `normalizeForCompare`, `fieldNames`, `opNames`, `pointCount` — reachable
  only from the above, so transitively dead

Only `sortMapKeys` and `jsonEqual` are live. And `sortMapKeys` (L282),
documented as "recursively sorts map keys for deterministic JSON output", is a
no-op: it builds a `map[string]any`, which is unordered, and `encoding/json`
already sorts map keys on marshal. Go does not flag unused functions, so this
compiles silently.

The dead code matters beyond tidiness: `structuralEqual` and
`deepEqualNormalized` are the *stronger* comparisons someone wrote and then
never wired up. The harness looks more thorough than it is.

### 3.5 CI never runs Go

`.github/workflows/build.yml` sets `defaults.run.working-directory: ts` and
runs only `npm ci`, `npm run build`, `npm test`. There is no `go build`, no
`go test`, no `make all`. **The entire Go port and every golden comparison are
local-only.** (`make check-model` is effectively covered, since
`ts/test/model-mirror.test.ts` asserts the same drift in the npm suite.)

### 3.6 The TSV fixtures miss the functions where the two actually differ

16 fixtures, ~318 data rows, covering 15 pure functions. Not covered:

- **`snakify` / `camelify` / `kebabify`** — see §6.1; these are the root cause
  of the largest naming divergence and have **no fixture at all**
- **`Validator` with an array argument** — the one branch where the two
  implementations differ structurally (§5.3). The TSV harness is
  string→string and *cannot express* an array input, so the format itself
  blocks coverage of the divergent branch
- `GetModelPath`; `Nom` beyond 9 rows; anything above the pure-function layer

`canonize.tsv` is a good illustration: it contains `API_Keys → api_key` (with
the underscore already present, where both agree) but not `APIKeys` — which is
exactly the shape that diverges.

Separately, `validator.tsv` **codifies a defect**: rows `unknown → Any` and
`foo → Any`. Every real validator token is backticked (`` `$STRING` ``,
`` `$ANY` ``); a bare `Any` is not a token, and emitting it into an `.aontu`
model yields an unresolvable identifier. Both implementations do this, and the
fixture now locks it in.

### 3.7 Loader asymmetry and no header validation **[code-read]**

`ts/test/tsv.test.ts` splits on `/\r?\n/`, with a comment recording the
Windows-only CI failure that motivated it. `go/tsv_test.go:loadTsv` splits on
`"\n"` only. `.gitattributes` (`*.tsv text eol=lf`) currently protects Go, but
the guard lives outside the loader and Go is not run on Windows CI anyway.
Neither loader validates the header row; the Go loader silently pads missing
columns. A renamed column therefore yields empty expectations rather than an
error — and for any function that can return `""`, that would pass.

### 3.8 Nothing enforces the stated invariants **[code-read]**

No check verifies that `// Mirrors src/…` comments point at files that still
exist, that every `ts/src/*.ts` has a Go counterpart, or that committed
`ts/dist` matches a fresh build.

On that last point, measured: `cd ts && npm ci && npm run build` with the
pinned `typescript@7.0.2` (and committed `package-lock.json`) leaves **24
`.js.map` files modified**. The emitted `.js` is byte-identical; only
`mappings` differ — e.g. `utility.js.map` 39,464 → 39,410 characters, 38 of
1,163 generated lines changed. So the committed artifact was produced by a
different compiler than the one now pinned. CI runs the build but never diffs
it against what is committed.

## 4. TypeScript findings

### 4.1 **[critical]** A spec with a schema named `Constructor` crashes the build

`IRREGULARS` (`ts/src/utility.ts:137`), `CUSTOM_PLURALS` (`:238`) and
`VALID_CANON` (`:~920`) are plain object literals used as lookup maps. A
prototype key therefore resolves to an inherited value rather than `undefined`:

```
depluralize("constructor")  => THROW: target.toLowerCase is not a function
depluralize("__proto__")    => THROW: target.toLowerCase is not a function
canonize("constructor")     => THROW: target.toLowerCase is not a function
validator("__proto__")      => Object.prototype        (an object, not a token)
validator("constructor")    => function Object() { [native code] }
```

`CUSTOM_PLURALS["constructor"]` yields `Object`, which is truthy, so
`if (customExact)` passes and `matchCase(word, Object)` calls `.toLowerCase()`
on a function.

End-to-end, on an otherwise ordinary OpenAPI 3.0 document containing
`components.schemas.Constructor`:

```
TS  ok: false | steps: ["parse"]
    TypeError: target.toLowerCase is not a function
      at matchCase (dist/utility.js:207)
      at depluralize (dist/utility.js:267)
      at canonize (dist/utility.js:807)
      at canonizeCmpName (dist/utility.js:835)
      at Task.MeasureRef (dist/guide/heuristic01.js:194)

Go  ok: true  | steps: [parse guide transformers] | entities: [constructor]
```

`canonize` runs on every path segment and schema name, so this is reachable
from any spec, not just a hostile one. `constructor`, `toString`, `valueOf`
and `hasOwnProperty` are all plausible schema names in a language-tooling or
metaprogramming API.

**Fix:** back all three tables with `Object.create(null)` or `Map`. `Map` is
preferable — `CANONIZE_CACHE` in the same file already uses it, so the
codebase's own precedent is correct; these three predate it. Add TSV rows for
`__proto__`, `constructor`, `prototype`, `toString`.

### 4.2 **[critical]** Chained `$ref` silently loses the schema, and the result depends on key order

`addXRefsAndResolve` (`ts/src/parse.ts`) replaces a `$ref` node with
`{ ...resolved, 'x-ref': xref }`. If the target is *itself* a bare `$ref`, the
copy retains a `$ref` **string** key — and the recursion that follows only
descends into object-valued keys. The chain is never followed.

Because `resolvePointer` reads from a root that the walk is concurrently
mutating, whether this bites depends on document order:

```
paths BEFORE components  ->  BROKEN (bare $ref, no properties)
components BEFORE paths  ->  RESOLVED ok
```

`paths` before `components` is the normal ordering. On the failing path the
operation's schema arrives downstream as `{ $ref, x-ref }` with no
`properties`, so every field is silently dropped — no warning, `ok: true`.

Go resolves it correctly in both orderings.

This is not hypothetical: `codatplatform-3.0.0-openapi-3.1.0.yaml` in the
corpus has exactly such an alias (`DataType: {$ref: …}`), and TS and Go
disagree about that spec's entity set (§6.2).

**Fix:** in `resolvePointer`, follow bare-`$ref` targets iteratively with a
visited set (which also terminates cycles), then inline. Add a fixture spec
with an alias chain in both key orderings.

### 4.3 **[medium]** `generate()` never returns `apimodel` on an early stop — contradicting the documented recipe

`ts/src/apidef.ts:220, 237, 252` (the `transformers`/`builders`/`generate`
early returns) all return `{ ok, steps, start, end, ctrl, guide }` — **no
`apimodel`**. But `AGENTS.md` documents:

> **Stop early:** … `generate:false` builds the model in memory without
> writing files.

and shows `result.apimodel.main.kit.entity`. Measured: with `generate:false`,
`result.apimodel` is `undefined`; the only way to obtain the model from TS is
to run the full pipeline and write files.

Go returns `ApiModel` from all three early returns (`go/apidef.go:164-165,
191-192, 209-210`) — which is why `go/validate_test.go` can read
`result.ApiModel` with `builders:false, generate:false`. That test could not
have been written against the TypeScript.

**Fix:** add `apimodel: ctx.apimodel` to the three TS early returns. Cheap,
and it makes the documented API true.

### 4.4 **[low]** `ok` is inconsistent across early stops

`parse:false` → `ok:true`; `guide:false` → `ok:false`; the other three →
`ok:true` (`ts/src/apidef.ts:112, 204, 220…`). Stopping deliberately after
parse is reported as a failure. Go mirrors this exactly (`go/apidef.go:83,
141, 164…`), so it is a shared design wart rather than a divergence — but it
makes `result.ok` unusable as a success signal for partial runs.

### 4.5 **[low]** `$ref` sibling keys are discarded **[code-read]**

`{ ...resolved, 'x-ref': xref }` drops anything that sat beside `$ref`.
OpenAPI 3.1 permits `description` and `summary` there, and JSON Schema
2020-12 permits arbitrary keywords. I confirmed the code shape but did not
construct an end-to-end case.

## 5. Go findings

### 5.1 **[critical]** `Validator` cannot represent unions, so nullable types collapse to `` `$ANY` ``

```ts
// ts/src/utility.ts:928 — canonical
function validator(torig: undefined | string | string[]): any {
  …
  else if (Array.isArray(torig)) return [CANON_ONE, torig.map(validator)]
```
```go
// go/utility.go:475 — port
func Validator(torig any) string {
  switch v := torig.(type) {
  case string: …
  default:     return "`$ANY`"      // arrays land here
  }
}
```

The return type was narrowed from `any` to `string` in the port, so the entire
array branch is unreachable. OpenAPI 3.1's `type: [string, "null"]` — the
standard way to express a nullable field — therefore degrades to `` `$ANY` ``.

Measured on `learnworlds-2-openapi-3.1.0`: **18 entities** differ, e.g.

| field | TS | Go |
|---|---|---|
| `affiliate.billing_info` | `` ['`$ONE`', ['`$OBJECT`','`$NULL`']] `` | `` `$ANY` `` |
| `assessment.grade` | `` ['`$ONE`', ['`$NUMBER`','`$NULL`']] `` | `` `$ANY` `` |
| `bundle.description` | `` ['`$ONE`', ['`$STRING`','`$NULL`']] `` | `` `$STRING` `` |

Go-generated SDKs lose all nullable/union type information for such specs.

Related, and separate: where Go *does* construct a union it uses a different
shape. `go/transform_args.go:117` emits a flat
`[]any{"`$ONE`", "`$NULL`", fieldType}` (3 elements), whereas TS emits a
nested `['`$ONE`', [t1, t2]]` (2 elements, second nested). Any consumer
pattern-matching on that structure sees two different formats.

**Fix:** change `Validator` to return `any` and mirror the array branch, using
`CanonOne` (already defined at `go/utility.go:469`). Normalise the
`transform_args.go` union to the TS shape. Then extend the fixture format —
see §7.

### 5.2 **[medium]** Go cannot load custom guide elements at all **[code-read]**

`go/resolver.go:resolveElement` returns
`fmt.Errorf("custom element loading not supported in Go: …")` unconditionally,
where TS `require()`s the module. Any guide using a `custom*` element works in
TypeScript and hard-fails in Go. This is a legitimate consequence of Go having
no runtime plugin story, but it is an unqualified functional gap that
`AGENTS.md`'s "must reproduce TS behaviour exactly" does not mention.

**Fix:** document the gap explicitly; consider a registration API so a Go
embedder can supply custom elements at compile time.

### 5.3 **[medium]** `ResolveElements` fails soft where TS fails hard **[code-read]**

TS: `guide.control[kind][subkind]` throws a `TypeError` if the guide is
malformed. Go: the chained `, _ :=` type assertions yield `nil`, `orderStr`
becomes `""`, `elementNames` is empty, and the stage **silently does
nothing**. A malformed guide produces a loud failure in one language and a
quietly empty model in the other. This pattern — single-line `, _ :=`
swallowing a structural error — recurs throughout the Go transforms and is
worth a sweep.

### 5.4 **[low]** Hand-rolled standard-library replacements **[code-read]**

`go/resolver.go:78-108` reimplements `strings.Split` and `strings.TrimSpace`
as `splitByComma` / `trimSpace`. Beyond being unnecessary, `trimSpace` handles
only ASCII space/tab/CR/LF, whereas TS's `.trim()` and `/\s*,\s*/` strip all
Unicode whitespace — so a guide `order` string containing NBSP or U+2028
parses differently in the two languages.

### 5.5 **[low]** `regexp.MustCompile` inside a hot function

`go/utility.go:341` (`Kebabify`) compiles `-+` on every call. Hoist to a
package-level var, as the file already does for `fileExtRE`, `booleanNameRE`
and others.

## 6. Reconciliation — where TS and Go actually disagree

### 6.1 Root cause: the Go port reimplements a *third-party dependency*

TypeScript imports its naming primitives:

```ts
// ts/src/utility.ts:4
import { snakify, camelify, kebabify, each } from 'jostraca'
```

Go reimplements them (`go/utility.go:313-345`, on a local `partify`).
Differential over 7,711 inputs:

| primitive | divergent | example |
|---|---|---|
| `snakify` | **662** | `APIKeys` → TS `api_keys`, Go `apikeys` |
| `camelify` | **1010** | `APIKeys` → TS `ApiKeys`, Go `Apikeys` |
| `kebabify` | **662** | `ABc` → TS `a-bc`, Go `abc` |

which propagates to the functions built on them:

| function | divergent / 7711 |
|---|---|
| `canonize` | 699 |
| `canonizeCmpName` | 699 |
| `validator` | 7 |
| `depluralize` | 2 (the `__proto__`/`constructor` crashes, §4.1) |
| `cleanComponentName`, `sanitizeSlug`, `slugToPascalCase`, `transliterate`, `normalizeFieldName`, `stripSchemaNamespace`, `ensureMinEntityName`, `inferFieldType`, `inferTypeFromValue` | **0** |

The clean columns are the ones with TSV fixtures. The divergent ones are the
ones without. That correlation is the whole argument for §7.

This is the deepest structural point in the review: **cross-language parity is
only as strong as the parity of the shared dependencies.** `jostraca`'s naming
functions are upstream code that Go has forked by hand, with no fixture and no
version pin relating the two. Any `jostraca` release can widen the gap
silently.

**Fix:** add `snakify.tsv`, `camelify.tsv`, `kebabify.tsv` seeded from a
generated corpus, exercised by both suites. Treat them as the contract with
`jostraca` and re-run on every `jostraca` bump. Note `camelify` feeds
`fixName`'s PascalCase form, so it determines generated SDK **class names**.

### 6.2 End-to-end model divergence on the real corpus

Both implementations run over `apidef-validate`, each from its own freshly
copied pristine guide tree, compared on the entity model (`active` stripped):

| spec | TS ents | Go ents | TS-only | Go-only | field-set diffs | field-type diffs | op-set diffs |
|---|---:|---:|---:|---:|---:|---:|---:|
| solar | 2 | 2 | 0 | 0 | 0 | 0 | 0 |
| petstore | 4 | 4 | 0 | 0 | 0 | 0 | 0 |
| taxonomy | 4 | 4 | 0 | 0 | 0 | 0 | 0 |
| **foo** | 7 | 7 | **2** | **2** | 0 | 0 | 0 |
| statuspage | 18 | 18 | 0 | 0 | **1** | 0 | 0 |
| pokeapi | 48 | 48 | 0 | 0 | 0 | 0 | 0 |
| shortcut | 37 | 37 | 0 | 0 | **2** | 0 | **2** |
| dingconnect | 17 | 17 | 0 | 0 | 0 | 0 | 0 |
| **cloudsmith** | **140** | **75** | **66** | 1 | 1 | 0 | 1 |
| contentfulcma | 39 | 39 | 0 | 0 | 0 | 0 | **1** |
| **learnworlds** | **41** | **29** | **12** | 0 | 0 | **18** | 0 |

The four small specs the parity test actually checks (solar, petstore,
taxonomy, foo) are the four cleanest — and even `foo` diverges.

**By cause:**

*Naming primitives (§6.1)* — mechanical, low-risk to fix:

- gitlab: `api_entities_mr_note` (TS) vs `api_entities_mrnote` (Go);
  `api_entities_ssh_key_with_user` vs `api_entities_sshkey_with_user`
- statuspage `metric`: fields `y_axis_min/max/hidden` vs `yaxis_min/max/hidden`

*Union types (§5.1)* — learnworlds' 18 field-type diffs.

*Classification* — the substantive one. TS promotes trailing action segments
to standalone entities where Go does not. cloudsmith has
`/files/{owner}/{repo}/{identifier}/abort/`,
`…/complete/`, `…/copy/`, `…/disable/`, `…/enable/`, `…/quarantine/`, and TS
emits entities named `abort`, `complete`, `copy`, `disable`, `enable`,
`quarantine`; Go does not. That is 66 TS-only entities on one spec. Given the
pipeline's own vocabulary — `guide` classifies paths into
"entities/ops/**actions**" — a trailing verb after an id ought to be an
*action* on the parent, so Go looks closer to intent here. But the judgement
is the maintainer's; what is not in question is that the same spec yields two
very different SDKs.

*Entity assignment* — shortcut: the same 5 fields and 4 ops (`create`, `list`,
`load`, `update`) attach to `comment` in Go and to `threaded_comment` in TS.
contentfulcma: `organization.load` exists only in Go.

### 6.3 Direction of the fixes

Per the project's own rule — *"Never make Go diverge from TS. If Go looks more
correct, fix TS first."* — note that **Go is the more correct side** for the
two most serious defects (§4.1 prototype-key crash, §4.2 chained `$ref`) and
arguably for classification (§6.2). So the mirroring in these cases runs
Go → TS: fix TypeScript to match what Go already does, then re-derive the
fixtures.

The rule holds; it is just being exercised in the direction the docs treat as
the exception.

## 7. Recommended fix for the parity mechanism

The TSV format did its job for the functions it covers — every fixture-covered
function is byte-identical across languages. Its limits are that it is
string→string and pure-function only, so it cannot reach unions, the naming
primitives, or anything above the utility layer.

Suggested, in dependency order:

1. **A real differential test.** One command that runs both implementations
   over the `apidef-validate` corpus, serialises each entity model to
   canonical JSON, and diffs. The harness written for this review is about
   120 lines total (a Node script and a Go `main`) and found everything in
   §6.2 on its first run. Check the *TypeScript* output in as the golden and
   assert Go against it — which also makes it obvious when the canonical side
   moves.
2. **Run Go in CI** (§3.5) and gate on that differential.
3. **Fixtures for `snakify`/`camelify`/`kebabify`** (§6.1) — the highest
   value-per-line addition available.
4. **Extend the fixture format for non-string arguments.** A JSON-valued
   column (as `infer-type-from-value.tsv` and `nom.tsv` already do for inputs)
   would let `validator.tsv` cover the array branch. Both loaders already
   `json.Unmarshal`/`JSON.parse` selected columns, so this is a small change.
5. **Regenerate the `apidef-validate` goldens** from current TypeScript and
   add a CI job that fails when they drift (§3.1).
6. **Delete or wire up the dead comparators** in `validate_test.go` (§3.4);
   promote `Logf` tolerances to `Errorf` (§3.3); move `model-ref/` out of
   `ts/test/` and rename it to say it is a Go snapshot (§3.2).
7. **Mechanical invariant checks** (§3.8): `// Mirrors src/…` targets exist;
   every `ts/src/*.ts` has a Go counterpart; `git diff --exit-code ts/dist`
   after a clean build.

## 8. Performance

Same stages both sides (`parse` + `guide` + `transformers`), single process
per language over the 14-spec corpus:

| spec | TS ms | Go ms |
|---|---:|---:|
| solar | 94 | 10 |
| petstore | 83 | 14 |
| taxonomy | 64 | 7 |
| foo | 35 | 5 |
| statuspage | 238 | 154 |
| pokeapi | 107 | 27 |
| shortcut | 264 | 195 |
| dingconnect | 50 | 49 |
| cloudsmith | 840 | 518 |
| contentfulcma | 240 | 66 |
| learnworlds | 351 | 165 |
| codatplatform | 213 | 113 |
| gitlab | 2247 | 835 |
| **github (8.8 MB)** | **5154** | **2885 – 6709** |

Go is 4–20× faster on small and mid-size specs but its advantage collapses on
the largest one, with run-to-run variance of more than 2×. CPU profile of the
github spec explains why:

```
runtime.scanobject              29.2% cum
runtime.memmove                  8.8%
runtime.memclrNoHeapPointers     8.6%
struct/go._walkDescend          14.2% cum
struct/go.Items                  8.2% cum
```

Roughly **45% of Go's time on the largest spec is GC and memory traffic**, not
algorithm. The cause is `map[string]any` as the universal model currency:
every scalar is boxed, every nested node is a separate allocation, and the
tree is walked repeatedly across nine transform passes.

Worth doing, cheapest first:

- pre-size maps and slices where the count is known before the loop
  (`make(map[string]any, n)`) — a large share of `memclr`/`memmove` is map
  growth;
- hoist package-level regexps (§5.5);
- reduce repeated full traversals: the nine transform passes each re-walk the
  model, and several only read. Fusing the read-only passes, or carrying an
  index built once, would cut `_walkDescend` directly;
- longer term, a typed model struct for the hot inner nodes (fields, ops)
  instead of `map[string]any` would remove most of the boxing. That is a large
  change and should follow the differential test, not precede it.

On the TS side the profile is less lopsided; the largest structural win there
is the same one — nine sequential full traversals of the model in
`ts/src/apidef.ts:221-229`.

## 9. Smaller notes

- `ts/src/apidef.ts` calls `Date.now()` at start and end and reports both, but
  `steps` is a flat `string[]` with no per-stage timing. Given nine transform
  passes, per-stage timings in the result would make performance regressions
  visible without a profiler.
- `peerDependencies` are all `">=0"` (`jsonic` is `">=2"`, `shape` `">=10"`).
  For a package whose output depends on `jostraca`'s naming functions
  (§6.1), an unbounded range on `jostraca` is a live parity risk, not just a
  supply-chain one.
- `apidef-validate/v1/diff-ts-go.md` is a committed Node stack trace from a
  missing `compare-ts-go.mjs`. Someone started building exactly the
  differential recommended in §7; the script did not survive.
